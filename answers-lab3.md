# Lab 3 Answers

**Q1 - version number and run artifact vs registered model**
The model was registered as version 1. A run's logged model artifact is tied to that specific run (stored via a run-scoped path/reference) - it's not independently addressable by a stable name. A registered model gives it a shared name (food11) and version number, decoupled from the run, so other code can reference models:/food11/1 or an alias without knowing which run produced it.

**Q2 - aliases replacing stages**
Aliases (champion, challenger, etc.) replaced the deprecated Staging/Production stages. A model is versioned separately from its run because the run captures one specific training execution (its exact code, data, hyperparameters, metrics) - a historical record that shouldn't change. The registered model is the deployable artifact serving code actually references, and it needs a stable identity independent of which run happens to be "best" right now. An alias is more flexible than a fixed stage name because you can reassign champion to a different version any time with one call - no fixed vocabulary forces your workflow into someone else's naming scheme, and you can invent as many aliases as you need.

**Q3 - loading via model URI vs .pth file**
Loading via mlflow.pyfunc.load_model("models:/food11@champion") instead of pointing at a .pth file directly means the serving code never needs to know which run produced the model, what the file path is, or how to reconstruct the model architecture before loading weights - mlflow's pyfunc wrapper handles all of that from registry metadata. To serve a newer model version, serve.py wouldn't need to change at all: reassigning the champion alias to a new version in the registry is enough, and the next container restart picks it up automatically. Pointing directly at a .pth file would require hardcoding a path and manually changing it every time you wanted to swap models.

**Q4 - copying pyproject.toml/uv.lock before src/**
Docker caches each build instruction and only re-runs it (and everything after) if its inputs changed. Since pyproject.toml/uv.lock change rarely but serve.py changes constantly during development, copying dependency files first and running uv sync before copying src/ means a code-only change skips the entire dependency install step on rebuild - Docker reuses the cached .venv layer and only redoes the src/ copy, making rebuilds seconds instead of minutes (confirmed firsthand: once cached, torch's ~400s download layer was skipped entirely on rebuilds that only touched serve.py).

**Q5 - image size**
The final multi-stage image is 2.08GB. docker history shows the single biggest layer is COPY /app/.venv /app/.venv at 1.5GB - the entire virtual environment (torch, torchvision, mlflow, etc.) copied in from the builder stage. Everything else is small: the Debian base layer is ~88MB, the Python interpreter install is ~46MB, my own src/ code is only 49KB. A naive single-stage build would be larger, since it would also keep uv itself, apt's package cache, and any build-time-only files a multi-stage build discards when the builder stage is thrown away. The application dependencies (mostly torch) dominate either way, so the multi-stage savings are real but modest in percentage terms here.

**Q6 - forgetting .dockerignore**
Without .dockerignore, the entire data/ folder (raw + processed Food-11 images, several GB) would get sent to the Docker daemon as build context on every build, slowing down every docker build invocation even when data isn't touched, and bloating the image if any COPY instruction picked it up. Of the excluded folders, .git/ and data/ would hurt build time/size most. .venv/ would actually break the build if copied in: it contains Windows-specific paths and binaries that don't work inside the Linux container, shadowing the correctly-built Linux .venv from Stage 1 with a broken one.

**Q7 - reaching the host mlflow server**
The container can't use 127.0.0.1:5000 because 127.0.0.1 inside a container refers to the container's own loopback interface, not the host machine - containers have their own isolated network namespace by default. host.docker.internal is a special DNS name Docker Desktop provides that resolves to the host's IP from inside the container. In practice this alone wasn't enough: the mlflow server also had to be started with --host 0.0.0.0 and an explicit --allowed-hosts list, since its security middleware rejects requests whose Host header isn't in an allowed list (host.docker.internal:5000 isn't localhost by default). Additionally, since the model's artifacts were stored via a local file:// path, the container needed that exact path bind-mounted in, because mlflow's local artifact store reads files directly off disk rather than fetching them over HTTP from the tracking server.

**Q8 - restarting from the same image**
Yes, a fresh container started from the same image loads the model correctly without any rebuild. This confirms the image itself is self-contained (code + dependencies baked in), while the actual model weights are fetched at runtime from the mlflow tracking server rather than baked into the image. This is the intended separation: the image is a reusable artifact for the serving code and environment, while the model version served is decided dynamically at startup via the champion alias - you can swap models without rebuilding, but the tracking server and artifact storage do need to be reachable at container startup, as confirmed when the container hung indefinitely while mlflow was temporarily down.

**Q9 - what's missing for portability**
The Dockerfile is versioned in git, but the built image (food11-api:latest) only exists locally - another machine has no way to pull it. Missing pieces: (1) pushing the image to a container registry (Docker Hub, GHCR, ECR) with an immutable tag (a commit SHA or semver), since "latest" isn't reproducible/traceable; (2) the mlflow dependency itself - this container only works if it can reach a running tracking server and its artifact store at startup, and right now that artifact store is a local file:// path on this specific Windows machine, which won't exist anywhere else - a portable setup needs a network-accessible tracking server backed by a real database and remote storage (S3/blob), not SQLite + local disk; (3) CI/CD wiring - something that automatically builds and pushes the image (e.g. GitHub Actions) so the registry image reliably matches what's in git, rather than relying on a manual docker build/push from a laptop.
